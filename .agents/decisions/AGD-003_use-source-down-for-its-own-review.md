## Context

Source Down 的第一个正式用户是自己的项目。通过自己的 Rust 文件和规范验证工作流，
能够同时检验源码阅读、插件边界和项目规则是否真正可组合。

## Decision

首版验收包含以下证据：

1. 构建出的主程序处理自己的真实 Rust 源文件，生成可返回原文位置的阅读材料。
2. 本项目在真实源码注释中注册并使用自己需要的指令，通过公开插件协议完成扩展；
   指令的具体功能在使用场景确定后由项目定义。测试语料至少使用两个不同名称，
   包含同名切换 owner 与一个插件注册多个名称的配置，验证请求到达所配置的处理程序。
3. 检查生成材料的代码字节、来源与批次调用计数，证明原文保留、位置可追溯以及批处理实际发生。
4. 在临时 checkout 中，分别制造坏指令语法、未注册名称、插件错误结果和遗漏响应，
   验证每类错误被报告，执行故障不会发布未验证产物，检查失败保留旧阅读页面。
   修复后必须重新通过正常生成。
5. 修改插件输入材料或参数后重新运行，再保持事实不变重复生成，
   验证新输入生效且相同事实产生相同字节。
6. 使用 OCaml 真实文件完成第二种语言的相同流程，验证项目插件机制与输入语言可独立组合。

先完成工具构建，再生成阅读材料。阅读材料的生成不作为源码编译的输入条件，
这样初次启动可从规范、代码与普通构建工具完成。

真实插件进程测试覆盖乱序/遗漏/重复响应、非零退出、管道容量和超时/取消。
性能实验按[工程交接](../../docs/engineering/README.md)记录工作量与环境；
先以真实进程证据核对启动与批次调用次数，
再以测量判断初始化、材料处理和输出的耗时瓶颈。

发布目标与精确工具链由首次发行切片记录，并对声明支持的每个平台验证实际产物。
包名、仓库名及发布渠道以实际可用命名空间为准。

## Consequences

第一位使用者与后续项目采用相同能力边界。首版必须包含 Rust 语言适配与可工作的自用扩展，
OCaml 示例或静态截图不能单独证明这个场景完成。
自用结果是生成契约和工作流的证据；代码是否符合全部产品要求继续按 Rule 0 审查。
