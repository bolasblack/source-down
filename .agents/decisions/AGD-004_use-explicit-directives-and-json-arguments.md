## Context

指令的业务含义由插件决定。注释中的常见调用只有一个路径或少量设置，需要便于手写和维护；
通用核心仍需可靠地区分字符串、参数、字面示例和错误输入。

## Decision

选择 `{% name arguments %}` 形式的模板标签作为扩展入口。
模板定界符使标签易于辨认，位置参数缩短常见调用，命名参数表达可选设置，点分名称便于组织相关指令。
解析后将位置参数数组与命名参数对象交给插件，使手写形式与传输数据各有明确表示。

使用只处理标量参数的有限标签解析器，
控制通用核心的语法范围；复用 JSON 转义便于交换数据，有限的单引号形式照顾手写场景。
材料选择和参数业务约束交给拥有该指令的插件，
使核心解析器可供不同项目复用。

Markdown 识别采用块级边界，代码示例与正文容器中的标签样式文字保持字面内容。
参数中的反引号可能影响普通 inline 解析，因此标签提取需要单独处理优先级。
对已进入标签语法的错误明确报错，使遗漏定界符或写错参数的问题能够被发现。

## Consequences

常见调用便于手写，代价是维护一个有限标签解析器和独立的 Markdown 优先级处理。
Markdown 解析器提供块级上下文，不能独自证明标签识别正确；固定语料覆盖参数、
字面容器、行尾和来源位置，验证手写便利性没有牺牲可靠识别。

## Reconsideration

多行参数和正文容器尚未采纳。如果出现实际需求，重新评估它们的来源范围、终止条件与解析优先级，
再在指令规范中定义采纳的形式。
