## Context

项目所有者需要用短编号展开规范，并发现不存在及未被引用的条款。
检查完整引用清单需要看到一次运行的全部输入，而阅读源码仍需要逐文件浏览。
这个场景也能检验首个使用项目是否真正通过公开协议扩展 Source Down。

## Decision

Source Down 项目将 `spec` 注册为自己的外部插件，入口位于 `tools/spec_plugin.rs`，
作为同一 Cargo 包的 example 构建。它复用通用 Markdown 章节解析和协议数据类型；
编号、规范目录、清单完整性与引用覆盖由项目插件负责。
插件在批次内为每份规范材料建立一次章节索引，按完整编号集中查找，
使多个请求与覆盖检查复用同一份解析结果。

`mise run build` 构建发行程序和项目插件；`mise run test` 与 `mise run check`
在执行测试前构建测试所需的插件。首次构建使用规范、源码及普通构建工具完成。

自用审查通过 `mise run review` 在同一次调用中选择 `src tools tests examples`。
验收对象为独立源码页面和插件报告；覆盖报告用于检查规范引用清单。原有语言、进程、确定性和故障注入验收继续适用，
并增加未知编号、定义歧义、零引用、部分引用，以及修复前后产物状态的真实进程证据。
验收同时核对诊断、报告和旧阅读页面的状态，避免仅凭退出码判断检查完整性。

## Consequences

实现和测试在各自拥有的行为附近引用相应条款。覆盖检查报告引用位置，
Rule 0 审查继续判断这些位置的实现是否满足规范含义。
源码包包含项目插件源码和构建任务；搬迁验收从解压源码构建该插件，
用实际归档程序及重新构建的程序比较各页面和报告的字节。
