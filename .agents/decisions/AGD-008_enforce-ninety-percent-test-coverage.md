## Context

项目所有者要求测试覆盖率至少为 90%。规范引用清单与执行过的代码是不同事实，
需要独立的覆盖率测量、明确分母和可失败的自动检查。
日常测试使用一个明确的任务入口，其成功包含测试通过和覆盖率达标。

## Decision

首版以代码行覆盖率作为数值门槛：Rust 主程序与库的 `src/**/*.rs` 合计至少 90%，
项目 Rust 插件 `tools/spec_plugin.rs` 和 Python 插件 `tools/project_docs.py` 各自至少 90%。
报告包含逐文件统计，避免主程序的体积掩盖项目插件的缺口。
测试源码、演示输入、开发辅助脚本、第三方依赖和生成代码不进入这些生产代码分母。
所有属于该范围的源码均须出现在报告中；零采样或遗漏文件使检查失败。
仅含注释和模块声明、没有可执行行的文件单独列入清单；新增可执行代码后自动纳入测量。

Rust 使用与固定 Rust 版本匹配的 LLVM coverage 工具及 cargo-llvm-cov；
Python 使用 coverage.py。工具版本和运行入口由 `.mise.toml` 固定。
测试任务以 `test` 为唯一名称。`mise run test` 准备工具环境，通过 `tools/test.py`
运行全部 Rust 和 Python 测试，从本次采样生成 HTML 与机器可读报告，并检查三个覆盖率门槛。
测试、采样、报告生成或门槛检查失败均使任务失败。

`check` 依赖 `test`，随后执行格式、Clippy、文档和 AGD 校验。
mise 的任务图复用同一次测试执行。

Rust CLI、项目插件的真实子进程和自用验收均使用本次插桩构建，
报告包含这些执行记录。测量任务独占采样目录，并在每次运行前清理旧记录，避免当前结果虚高。
比较使用原始计数，展示时的四舍五入不能使低于 90% 的结果通过。

未覆盖代码用于寻找缺少的行为案例。新增测试继续遵循既有公开接口、文件、进程和发布边界，
验证要求的结果；修复行为缺陷时先观察相应测试失败。

## Consequences

覆盖率报告定位仍未执行的代码；规范符合性、断言质量和错误边界仍按 Rule 0 审查。
默认测试入口提供完整的测试和覆盖率验收证据，检查成本包含插桩构建与采样。
源码搬迁后沿用相同工具配置和覆盖率门槛。
