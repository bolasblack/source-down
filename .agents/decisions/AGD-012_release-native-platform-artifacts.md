## Context

项目所有者要求发布 Linux x86-64 与 ARM64 的 GNU、musl 版本，macOS ARM64，以及 Windows x86-64。
这些目标包含不同的链接器、归档格式、文件标识和进程 I/O 机制。
一次交叉编译成功不能证明产物能够运行，也不能证明取消和插件清理的行为。

## Decision

发布流程为六种目标分别构建原生程序。Linux 与 macOS 使用 tar.gz，Windows 使用 zip；
另交付一份可搬迁源码归档。每次发行只有一份覆盖完整附件集合的 SHA256SUMS。

Linux x86-64 GNU 执行完整开发验收，包括覆盖率、自用和性能检查。
每个目标在对应操作系统和架构的 runner 上执行实际程序及插件验收；musl 产物还须验证静态链接。
目标平台、命令、附件清单和固定的 Action 版本统一记录在仓库发布契约中。

所有操作系统条件编译与原生 API 集中在一个 platform 兼容模块中；CLI、插件协议、渲染、搜索和发布逻辑调用同一套接口。
协议状态、截止时间和诊断仍由会话 I/O owner 负责。平台适配提供路径表示、文件身份、显式关闭、取消通知、可取消输出与插件进程作用域，
Unix 使用进程组，Windows 使用在执行插件前建立的 Job Object。取消和失败清理包括持有管道的后代。
平台差异不能通过关闭插件功能、跳过输出检查或忽略清理失败来消解。

评估的 process-wrap 9.1.0 通过 nix 要求的 libc 版本与现有固定版本冲突，本次使用已存在于依赖图中的 windows-sys 绑定，避免为进程作用域修改无关依赖。
Windows 的同步管道由兼容模块内的工作线程拥有；有界读队列与至多一个未完成写入限制额外内存，写入确认发生在实际写入和 flush 后。
取消同步 I/O 后必须等待线程完成；重复取消覆盖停止标记检查与进入系统调用之间的窗口。协议截止时间仍由原来的单一驱动器负责。
进程作用域在任何后续可失败的管道或消息初始化前就获得 RAII 清理保护；正常路径显式关闭并报告清理错误。

CI 的构建和验收 job 只拥有仓库读取权限。只有完整附件集合通过验证后，单独的 job 才拥有创建或更新未发布草稿的权限，
该 job 不执行仓库代码。发布仍需要独立的人类决定；已发布的身份和附件不能由构建流程改写。

## Consequences

原生 runner 增加 CI 用时，但直接覆盖目标操作系统上的启动、文件操作和插件行为。
本机只能为实际执行过的目标提供运行证据；其他目标的运行结果由对应 CI job 提供。
源码归档的搬迁重建在 Linux x86-64 GNU 上执行，与各平台二进制的运行验收分别报告。
新增发布目标时，需要同时定义附件、工具链和原生验收入口。
