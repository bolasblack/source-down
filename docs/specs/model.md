# 模型与责任

Source Down 是文学化编程工具，其创作方式、阅读输出与扩展边界由 [SPEC-MOD-001](#spec-mod-001) 定义。

<a id="spec-mod-001"></a>
## SPEC-MOD-001 产品边界

作者以原生源文件共同编写程序叙述和实现：在注释中解释问题、设计依据与算法步骤，在代码中表达实现，并通过指令引入相关材料。Source Down 将这些内容编织为可阅读、可追溯的程序表达，支持作者在修改程序时共同维护说明与代码。

输入为一次调用选择的本地源文件和 Markdown 叙述文档、项目配置及项目插件读取的本地材料。每个选中的输入文件对应一个 Markdown 页面。源码页的注释成为正文，代码进入带语言标记的代码块，项目指令在原位置展开为插件返回的内容。Markdown 叙述页保留作者文字并执行自身指令，按作者顺序组织材料。页面路径保留输入文件的目录结构和完整文件名，具体映射由 [CLI 输出布局](cli.md#spec-cli-007) 定义。

插件处理一次运行的完整输入清单及属于自己的全部指令调用，可以同时返回指令展开、指定页面的附录、独立报告和诊断。一个批次可以影响多个页面；页面的数量和插件的调用次数分别遵循[渲染](rendering.md#spec-ren-007)与[批次](plugins.md#spec-plg-003)契约。

源文件与被引用文档保持各自的权威。生成物是一次运行读取事实的阅读投影。代码设计、修改、编译、执行与语义符合性判断由使用者的开发和审查流程承担。

Source Down 的核心拥有通用指令语法与调用协议。发行物提供[内置插件](standard-directives.md)，项目可以注册额外指令与显式替换内置指令的处理程序；核心依照[注册规则](cli.md#spec-cli-003)把指令交给唯一 owner。每项指令的参数语义和结果产生方式由其 owner 定义。Source Down 自己也是使用这些能力的一个项目。

<a id="spec-mod-002"></a>
## SPEC-MOD-002 核心概念与 owner

| 概念 | 含义 | 语义 owner |
| --- | --- | --- |
| Project root | 本次输入、配置与来源路径的共同根 | [CLI](cli.md) |
| Document kind | Source（具备源码语言）或 Markdown（作者叙述）；不将 Markdown 伪装为注释 | [源码转换](rendering.md#spec-ren-014) |
| Source file | 已选定路径及本次读取的原始字节 | [CLI](cli.md) |
| Source span | 某份原文中的非空区间 | SPEC-MOD-003 |
| Prose / Code segment | 提取的正文或保留的源码片段 | [源码转换](rendering.md) |
| Directive occurrence | 一个正文位置上的项目指令 | [指令语法](directives.md) |
| Plugin instance | 一个启用的内置处理程序或项目配置的插件条目；处理自己的指令与运行级工作 | [CLI](cli.md)与[内置目录](standard-directives.md) |
| Content description | 插件返回的有序 text / standard_call 节点或单块 Markdown 形式 | [插件协议](plugins.md#spec-plg-006) |
| Expansion | 某次作者指令的已求值 Markdown 块序列及每块来源 | [插件协议](plugins.md#spec-plg-007) |
| Source page | 一个所选输入文件对应的独立 Markdown 页面；以该源文件的规范相对路径标识 | [源码转换](rendering.md)、[CLI](cli.md) |
| Page appendix | 插件指定追加到某个 Source page 末尾的 Markdown 和来源 | [插件协议](plugins.md#spec-plg-011) |
| Report | 插件拥有的具名运行结果；由核心发布为独立 Markdown 文件 | [插件协议](plugins.md#spec-plg-011)、[CLI](cli.md) |
| Diagnostic | 插件完成检查后报告的 warning 或 error，可定位到原文 | [插件协议](plugins.md#spec-plg-012) |
| Session | 固定 project root、有效配置、输出位置和插件注册集合的一段生命周期 | SPEC-MOD-004、[SPEC-PLG-003](plugins.md#spec-plg-003) |
| Dependency | 可能改变本轮计算结果的文件系统事实，独立于 SourceSpan | [SPEC-PLG-013](plugins.md#spec-plg-013) |
| Run | 一组输入的一次完整生成尝试 | SPEC-MOD-004 |
| Review artifact | 成功发布的源文件阅读页面 | [源码转换](rendering.md)、[CLI](cli.md) |

插件拥有参数解释、项目材料选择、检查规则和报告内容。核心拥有源码分段、调用归属、响应完整性、来源验证、页面组装、输出路径和发布。插件的实现语言由项目选择。
项目可以声明对发行版标准内容操作的委托，核心求值并保存有序块及实际材料来源。
委托保持其父内容身份，不产生新的作者指令；来源仍是实际原文区间。

<a id="spec-mod-003"></a>
## SPEC-MOD-003 原文与来源区间

源码、引用材料与插件 Markdown 使用有效 UTF-8。源码和引用文本接受 LF、CRLF 和缺少文件末尾换行；拒绝 UTF-8 BOM、NUL 与非法 UTF-8。位置以实际读取的字节计算。原文中的 CRLF 占两个字节。

`SourceSpan` 是下列封闭对象，字段均必填：

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| `path` | string | project root 内文件的规范相对路径；使用 `/`，非空，组成部分为实际文件名，排除空、`.` 和 `..` 部分 |
| `start_byte` | integer | 零基、含起点，`0 ≤ start_byte < end_byte` |
| `end_byte` | integer | 不含终点，至多为文件字节长度 |
| `start_line` | integer | 起点所在行，一基 |
| `end_line` | integer | `end_byte - 1` 所在行，一基、含终点 |

所有整数为 `0..9007199254740991` 内精确整数，行号从 1 起。行由 LF 分隔，CRLF 计一次换行。byte 边界必须位于 UTF-8 字符边界；行号必须与 byte 区间一致。绝对路径只用于进程调用上下文；最终来源显示采用相对路径。参与源码与来源显示的路径及其组成部分必须是有效 UTF-8，排除 U+0000–U+001F 和 U+007F 控制字符；不满足时明确报路径错误。

核心验证来源文件存在且区间合法。来源证明内容可追溯到哪里；把多个材料综合生成一段文字是否正确，由插件与审查者判断，不能仅从区间合法推导。

<a id="spec-mod-004"></a>
## SPEC-MOD-004 一次运行的事实与顺序

会话串行执行多轮；一轮已验证结果须发布或丢弃后，才能开始下一轮。每轮重新选择文件、读取字节、解析源码并发现指令；文件存储和索引限定在本轮，不复用上轮文件事实。

一次运行按[文件选择规则](cli.md#spec-cli-002)确定输入集合，保存每份源码本次读取的完整字节，按[源码转换](rendering.md)取得分段和指令，再执行[插件批处理](plugins.md)。每个插件取得相同的完整输入清单，包括未使用任何指令的文件。每条指令保留独立身份，响应顺序不改变它在所属页面的位置。

在输入字节、路径、有效配置、插件返回结果和输出目录相同的条件下，本次页面及报告的路径和字节必须一致；时间戳、随机 ID 与进程调度不进入正文。插件的环境与材料是项目负责稳定的输入事实。

核心把源文件及来源材料在本次运行中校验过的字节用于排版与位置解释；同一路径按一个读取版本验证。运行期间文件被其他进程修改，不具备全仓库原子快照保证。可复核的审查由项目在稳定的 checkout 上执行。

<a id="spec-mod-005"></a>
## SPEC-MOD-005 成功与失败的含义

生成成功要求：输入集合合法、源码边界可可靠识别、所有启用插件完成有效批次、所有指令取得成功结果、诊断中没有 error、所有来源及将发布的 Markdown 通过格式检查，且本次页面与报告发布成功；单次 render 还须在发布前正常关闭外部插件会话。warning 可以与生成成功同时存在。
插件返回待求值的内容描述尚不表示成功；标准调用也须完成，且三种输出位置的内容均须完整有效。

有效响应中的请求错误或 error 诊断表示已完成处理并发现问题；核心收集其他批次的有效结果，发布报告，保留原有阅读页面，并以失败退出。进程异常、协议非法或来源无法验证表示执行故障。两类失败的中止和发布规则分别由[插件协议](plugins.md#spec-plg-008)及 [CLI](cli.md#spec-cli-004) 拥有。

生成成功证明选定材料按本规范转换，且所启用插件没有报告检查错误。插件可以检查本次输入中的引用覆盖，但其清单范围、编号含义与通过条件由插件定义。是否实际实现某条规范、类型是否表达全部要求、审查能否发现全部偏差，需要对应的语义审查证据。

插件是项目配置的本地程序，具有启动环境授予的进程权限。核心对自己读取与写入的文件和插件调用执行本规范；插件自行造成的外部作用由项目插件承担。

## 验收场景

| 条款 | 输入与动作 | 可观察结果 |
| --- | --- | --- |
| SPEC-MOD-001 | 同一指令名在两个项目注册不同插件 | 核心使用各项目的插件结果 |
| SPEC-MOD-001 | 同一次调用选择 implementation、interface 与其他语言文件 | 每个源文件各有一页，完整文件名保留；插件仍按整次运行处理 |
| SPEC-MOD-003 | 中文、CRLF、行尾边界和越界 source span | 正确区间接纳，错误区间导致生成失败 |
| SPEC-MOD-004 | 相同事实连续执行两次，指令结果项和报告对象成员调换顺序 | 页面与报告的路径、字节相同 |
| SPEC-MOD-005 | 其中一个指令失败，另一个插件完成检查并返回报告 | 本次生成失败，报告发布，旧页面保持；发布遵循 CLI 契约 |
| SPEC-MOD-005 | 插件完成检查并仅返回 warning | 显示诊断，页面及报告正常发布 |
