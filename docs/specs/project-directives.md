# 本项目的 spec 指令

本页拥有 Source Down 仓库作为使用项目注册的 `spec` 指令。项目配置选择其独立插件入口；通用核心按[插件协议](plugins.md)处理结果。其他项目可以复用这个插件或注册自己的同名指令。`package` 和 `modules` 示例由[项目工具说明](../../tools/README.md)描述。

<a id="spec-prj-001"></a>
## SPEC-PRJ-001 编号与展开

```text
{% spec "plg-001" %}
{% spec "PLG-001" %}
{% spec "SPEC-PLG-001" %}
```

`spec` 恰好接受一个字符串位置参数，named 参数为空。编号接受 ASCII 大小写不敏感的 `DOMAIN-NNN` 或 `SPEC-DOMAIN-NNN`；DOMAIN 由一个或多个 ASCII 字母组成，NNN 为 `001..999` 的三个十进制数字。规范身份统一为大写 `SPEC-DOMAIN-NNN`。其他格式、参数类型、数量或命名参数返回请求级 `invalid_arguments`。

编号唯一存在时，结果展开该条款的完整原文，包括紧邻的规范锚点、标题、正文和更低级标题，直到下一个同级或更高级的顶层标题之前或文件结束。字节、CRLF 和末尾换行保留；成功来源为该材料实际选区。Markdown 标题与章节范围遵循 [SPEC-BLT-004](standard-directives.md#spec-blt-004) 的通用章节识别规则。

插件成功响应使用一个 `standard_call` 内容节点，directive 为 `include`，唯一位置参数为本轮已定位定义的文件路径，named 恰好为 `lines: [start_line, end_line]`。行号来自该完整定义的实际 SourceSpan；末行是 `end_byte - 1` 所在的物理行。核心执行 include 后取得相同的原文字节区间和来源。插件不在成功项中预填材料 sources，也不通过 anchor 重新查找选区；其他层级标题复用该 anchor 不影响已经确定的定义。每轮重新计算范围，条款前插入文字或改变条款末尾后，节点行号随定义更新。

这一行范围形式适用于完整 LF 物理行选区：起点是文件开头或 LF 之后，终点是 EOF 或 LF 之后。CommonMark 也将孤立 CR 识别为标题换行，章节边界可能落在同一 LF 物理行内。该区间无法由 lines 精确表达时，插件使用协议已有的 `markdown, sources` 形式返回精确章节字节与原始 SourceSpan；不得将选区扩大到整行。孤立 CR 只出现在选区内部而两端仍对齐时，继续使用标准调用。定义、锚点和引用统计规则对两种形式相同。

不存在的编号返回请求级 `spec_not_found`，诊断保留该指令的原始位置。重复定义的编号返回 `spec_ambiguous`，完整定义位置由 SPEC-PRJ-002 的运行级诊断列出。每个请求都返回独立结果，多个位置引用同一条款是合法的。

<a id="spec-prj-002"></a>
## SPEC-PRJ-002 清单与定义完整性

插件的 options 是封闭对象，允许字符串 `spec_dir`，默认 `docs/specs`。该路径遵循 project-relative 路径规则，须指向 project root 内的目录。递归读取其中常规 `.md` 文件，按规范路径排序；目录中的符号链接使清单读取失败。不可读目录、非法路径或文本使插件执行失败，核心按公开协议报告故障。

每轮按 [SPEC-PLG-013](plugins.md#spec-plg-013) 声明 spec_dir 的递归 directory 依赖及全部读取的 Markdown 文件依赖，包括没有匹配条款的文件。每轮重新读取目录和文件并建立索引；有效检查失败仍完整返回依赖，目录或材料读取失败继续按执行故障处理。

定义取自 CommonMark 顶层二级标题：标题文本以完整、大写 `SPEC-DOMAIN-NNN` 开始，随后为空白或标题结束。代码块、HTML 块、列表、引用块中的编号，以及普通正文中的引用不构成定义。每条定义紧邻的显式锚点须等于完整编号的小写拼写。

全目录的定义按完整编号匹配。一份材料在该批次中只读取一次，各次展开、定义诊断与报告使用同一份材料字节。缺少或错误锚点产生 `spec.invalid_definition` error 诊断；一个编号有多个定义时产生 `spec.duplicate` error 诊断，并保留全部定义来源。清单能完整读取但没有条款时，产生 `spec.empty_inventory` error 诊断。

有歧义或格式错误的定义不能提供成功展开；相应请求返回 `spec_ambiguous` 或 `spec_invalid_definition`。这些定义问题通过完整响应报告，其余请求仍取得自己的结果，coverage 报告仍描述本次已读取的清单与问题。

<a id="spec-prj-003"></a>
## SPEC-PRJ-003 引用覆盖与报告

本插件收到一次运行中全部所选源文件的清单和所有属于自己的 `spec` 调用。引用统计只计成功解析到唯一、合法定义的调用；字面示例、普通注释里的编号、其他指令及错误调用均不增加引用数。重复的合法引用分别保留其调用位置。

成功项委托的标准 include 不创造新请求、不增加引用计数。插件在返回完整响应前完成本轮定义检查与引用统计，不等待核心回传材料。委托的内容错误遵循 [SPEC-PLG-008](plugins.md#spec-plg-008)，使本轮检查失败；它不能将失败的生成变为成功。

完整清单中每条合法且唯一的定义须至少被本次输入引用一次。未引用集合非空时，返回 `spec.unreferenced` error 诊断，message 列出全部缺失编号，sources 指向对应定义。即使 requests 为空也执行这项检查；本次仅选择部分源文件时，仍以配置指定的完整清单检查该输入范围。

每次完成检查都返回名为 `coverage` 的 Markdown 报告。报告按完整编号排序，列出每条定义的状态、全部引用的源文件及一基行号，并单独列出未知请求与定义问题。无缺失时也返回当前通过结果，覆盖上一次报告。报告声明实际使用的定义和调用来源，核心按输出布局生成可导航的来源链接并显示完整输入清单。

请求错误、定义错误或未引用条款使 CLI 检查失败，报告仍按 [SPEC-CLI-004](cli.md#spec-cli-004) 发布。编号清单和引用位置证明本次的引用覆盖；代码与条款的语义符合性由审查判断。

## 验收场景

| 条款 | 输入与动作 | 可观察结果 |
| --- | --- | --- |
| SPEC-PRJ-001 | 短编号、不同大小写及完整编号指向同一条款 | 展开相同原文，保留锚点、子标题和精确来源 |
| SPEC-PRJ-001 | 未知编号、错误参数与两个重复的合法引用 | 未知和错误参数分别定位；合法重复调用均展开并进入引用索引 |
| SPEC-PRJ-001 | 材料含 CRLF、中文、无末尾换行及后续同级标题 | 只展开对应完整章节，字节与来源区间准确 |
| SPEC-PRJ-001 | 普通子标题复用定义 anchor；观察真实插件响应及最终页面 | 返回按已定位定义计算的 lines 数组；include 不重查 anchor，原文字节和来源相同 |
| SPEC-PRJ-001 | 同一会话两轮间在定义前插入文字或改变末尾 | 每轮节点采用当轮路径与行号；页面和覆盖报告同步更新 |
| SPEC-PRJ-001 | 孤立 CR 使相邻定义落在同一 LF 物理行内 | 返回精确 Markdown 与 SourceSpan，各请求只展开自己的条款；不会用相同的 lines 扩大选区 |
| SPEC-PRJ-002 | 同编号分别出现在两个文件；另有仅在代码示例中出现的标题 | 真实重复定义报错并列出双方位置，示例不进入索引 |
| SPEC-PRJ-002 | 错误或缺失锚点、空清单、根外目录或符号链接 | 可读取的定义问题产生完整诊断和报告；读取失败按执行故障处理 |
| SPEC-PRJ-003 | 两个源文件分别引用两个条款 | 一次批次检查通过，两份页面生成，报告记录各自位置 |
| SPEC-PRJ-003 | 一个条款遗漏，或整个批次没有指令 | 报告列出所有未引用条款，CLI 退出 1，旧页面保持 |
| SPEC-PRJ-003 | 修复遗漏后再次运行 | 报告更新为当前通过结果，页面发布成功 |
| SPEC-PRJ-003 | 只在 fenced 示例、普通注释或 include 指令中提到编号 | 该条款仍被报告为未引用 |
